# Wabi Insight — Security

Status: P12.1 — hardening complete for v1. Each section names the phase that introduced it; the P12.1 section at the end lists the platform-wide controls and the verification suite.

## Account model
- Two stores, one login screen. `Administrators` (platform company, no `OrganizationId`) and `OrganizationUsers` (required `OrganizationId`). `LoginIdentities` (primary key `NormalizedEmail`) resolves the account category and makes a login email unique across both stores.
- Emails are normalized (trimmed, upper-invariant) before lookup; the original casing is kept for display.
- Passwords are hashed with ASP.NET Core Identity's `PasswordHasher` (PBKDF2-HMAC-SHA512, per-password salt, v3 format). Hashes are re-hashed transparently on login when the algorithm parameters change. No custom cryptography.

## Password policy
Length only (NIST SP 800-63B): 12–128 characters, not equal to the login email, not the known sample password. The sample password `my_default_password_change_it` is accepted **only** when the host environment is `Development` and only for bootstrap; every other environment rejects it, and the change-password endpoint rejects it everywhere.

## Login behaviour
| Case | Response |
|---|---|
| Unknown email or wrong password | 401, identical problem type `invalid_credentials`; a dummy hash verification equalizes timing for unknown emails |
| 5 failed attempts (configurable) | account locked for 15 minutes (configurable); further attempts return `locked_out` even with the right password |
| Inactive account | `account_disabled` |
| User of a suspended/deactivated organization | `organization_suspended` |
| More than 10 login attempts per minute per client (configurable) | 429 |

Every outcome is written to `AuditLogs` (`Auth.LoginSucceeded`, `Auth.LoginFailed`, `Auth.LoginDenied`, `Auth.LockedOut`) without the password.

## Sessions
- Cookie `wi.session`: `HttpOnly`, `SameSite=Lax`, `Secure` when the request is HTTPS, not persistent. Sliding idle timeout 30 minutes and absolute lifetime 12 hours (both platform-configurable); 401/403 are returned as JSON, never redirects.
- The cookie carries only identifiers and the security stamp. The security stamp is re-validated against the database at most every 5 minutes (configurable, 0 = every request): a changed password, an administrator reset, deactivation, lockout or organization suspension ends the session on the next validation.
- `change-password` rotates the security stamp (invalidating every other session) and re-issues the current session.
- `must_change_password` sessions can reach only `me`, `csrf`, `logout` and `change-password`; everything else returns 403 `password-change-required`.

## Antiforgery (CSRF)
Double-submit pattern: `GET /api/auth/csrf` issues the `wi.xsrf` cookie and returns the request token; every unsafe request (POST/PUT/PATCH/DELETE) must send it in `X-XSRF-TOKEN`. Tokens are bound to the identity, so clients fetch a new one after login. Validation is default-on for all controllers; `logout` and `csrf` opt out explicitly. Failures return 400 `antiforgery`.

## Organization roles
`Roles` and `UserRoles` are organization-scoped with composite foreign keys that make cross-organization assignments impossible at the database level. Role codes travel in the session as `role` claims, refreshed with the security stamp, and feed the `OrganizationAdmin` policy. Organization onboarding is the one path where a Platform Administrator creates an organization user (the initial administrator); its temporary password is emailed and the account must change it at first sign-in.

## Organization structure and user management
Departments, sections and users are tenant-filtered and additionally bound by composite foreign keys (`OrganizationId` travels with every department, section and role reference), so a mismatched section/department or a cross-organization role assignment fails in the database even if application code regressed. Organization Administrators cannot deactivate their own account, remove their own administrator role, or leave the organization without an active administrator. New users and resets go through the same emailed temporary-password flow as administrators.

## Authorization
- Fallback policy: every endpoint requires an authenticated session unless it carries `[AllowAnonymous]` (login, csrf, bootstrap, platform info, health). Unknown routes return 401 to anonymous callers.
- Policies: `PlatformAdministrator` (principal type claim), `OrganizationUser` (principal type + organization claim), `OrganizationAdmin` (organization user with the `OrganizationAdmin` role claim).
- Tenant context: `TenantContextMiddleware` rebuilds the trusted `TenantPrincipal` from the cookie after authentication. A platform administrator carrying an organization claim, or an organization user without one, is treated as unauthenticated.

## Bootstrap (first Platform Administrator)
- Configuration `Bootstrap:*` is read from environment variables, user secrets or a secret store. Only the Development sample file commits sample values.
- Two entry points share `BootstrapService`: the `bootstrap` CLI command (uses the configured secret) and `POST /api/bootstrap/initialize` (requires the secret in the body, rate-limited to 3/min per client). `GET /api/bootstrap/status` reveals only completion state, date, the bootstrap email, schema version and whether migrations are pending.
- Preconditions: bootstrap enabled, a secret of at least 16 characters, plausible email, policy-compliant password, schema at the latest migration, no completed `SystemInitialization` row and no existing administrator.
- Effects, in one transaction: administrator with `IsBootstrapAdministrator = true` and `MustChangePassword = true`, login identity, singleton initialization row, `Bootstrap.Completed` audit entry. The singleton check constraint and the filtered unique index make concurrent attempts fail atomically; the loser receives 409.
- Migrations are never applied by the bootstrap request. Use the `migrate` command at deployment time.

## Account provisioning and temporary passwords
`POST /api/platform/administrators` (create) and `POST /api/platform/administrators/{id}/reset-password` are restricted to platform administrators. Both generate a cryptographically random 20-character temporary password, store only its hash, and **email** it to the account owner (bilingual template, RTL for Arabic). The API response carries the masked recipient address and the outbox message id, never the password; the administrator who triggered the action does not see it. The target account gets a new security stamp (existing sessions end), `MustChangePassword = true` and cleared lockout; the first sign-in is forced through change-password. Self-reset is refused; use change-password.

## Email delivery
Settings live under `Email` (`Provider` = `Smtp` | `File` | `None`). SMTP uses MailKit with STARTTLS on port 587 (implicit TLS on 465); plain connections are refused when `EnableSsl` is true. Messages go through an outbox: the `EmailMessages` row stores recipient, subject, template code, language, status (`Queued`, `Sent`, `Failed`), attempts, last error and the requesting principal, and the body is kept only in memory until the background worker delivers it (bounded retries, configurable delay). Credentials therefore never reach the database or the logs. The committed SMTP password is a placeholder; supply the real one through `appsettings.Local.json` or the deployment configuration. `DkimSelector` is accepted for future DKIM signing but not applied in v1.

## Configuration database connection string
By owner decision G (see `docs/SPEC_REVIEW.md`), the connection string is committed in `appsettings.json` for this private repository. Treat repository read access as database access.

## Platform operations data
Platform Administrators read aggregates (`/api/platform/dashboard`), health (`/api/platform/health`) and the audit trail (`/api/platform/audit`). The dashboard counts applications but never returns their names or connection details; audit details never contain secrets or business data; unhandled exceptions are recorded as `Api.Error` usage events with the exception type only, never its message. `UsageEvents` and `AuditLogs` are both append-only. Since P13.11 the compiled SQL never reaches the browser: each question is recorded in the append-only, tenant-filtered `AnalysisQueryLogs` (question, validated plan, SQL with bound values, row counts, outcome) for accuracy reviews, and no endpoint returns it; the page explains the validated plan in words from the catalogue's display names.

## Support desk
Ticket visibility is decided from the tenant context only: a requester sees their own tickets, an `OrganizationAdmin` every ticket of their organization, a Platform Administrator the platform queue. A ticket of another organization is a 404, even by id. Status changes follow the fixed transition table (`TicketStateMachine`); anything else is rejected with a stable code. Attachments: 10 MB, extension allow-list (`pdf, png, jpg, jpeg, xlsx, docx, csv, txt, log, zip`), SHA-256 recorded, scanner hook (`IAttachmentScanner`), stored outside the web root under random keys and served only through the authorized download endpoint with `nosniff`; Platform Administrator downloads are audited (review C6). `SupportTicketEvents` is append-only. Notifications are readable and markable only by their recipient.

## Support access (scoped administrative assistance)
A Platform Administrator never changes an organization's configuration without an approved, unexpired, narrowly scoped `SupportAccessGrant`; a ticket alone grants nothing. Grants list typed operations with specific target ids (validated to belong to the ticket's organization); there is no global grant and no business-data operation. Approval requires an active `OrganizationAdmin` of that organization; `RequireSecondAdminApprovalForSupportAccess` forces a different administrator than the requester. Execution requires an explicit support-mode session of the assigned administrator (`SupportMode` policy) and passes `SupportAccessAuthorizer` per call: assignment, expiry (default 4 h, max 72 h), operation and target scope. Denials are audited (`SupportAccess.OperationDenied`). Any `OrganizationAdmin` of the organization or any Platform Administrator can revoke immediately, which ends the session. Every executed operation is written to the ticket timeline, `AuditLogs` and `UsageEvents` with administrator, organization, ticket, grant, session, operation, target and outcome; temporary passwords are emailed to the user and never appear in results or details.

## Application connections and metadata
Connection strings are encrypted with ASP.NET Core Data Protection (purpose-specific protector, file-system key ring outside the configuration database, automatic rotation with old keys retained) and are never returned by any endpoint; the API shows "configured" plus the hint typed by the administrator. A salted HMAC fingerprint makes a source unique across the platform, so two organizations can never register the same database (A7). Adapters open sources with read-only intent, read catalog views only and never execute anything but fixed discovery queries; the connection test reports whether the account is read-only and warns otherwise. Metadata is per organization through the tenant filter; Platform Administrators reach it only through an approved `RefreshMetadata` or `DiagnoseApplicationConnection` grant, and have no application endpoints. Business descriptions are user content (length-limited) and will be passed to the LLM as delimited data, never as instructions.

## Permissions (P6.2)
Business data access is decided only by the resolver: organization boundary first, then approved applications, approved objects and columns, then the union of the user's active roles. `Management` is automatic (all approved objects, all rows) and cannot be edited; `OrganizationAdmin` manages configuration and grants no data by itself. Row scopes `Department`, `Section` and `Self` require a mapped column on the object; without it the user sees the columns but no rows, never all rows. Grants are written only by Organization Administrators of that organization or, under an approved support grant, through the `UpdateTablePermissions` operation targeting a listed role; every change is audited (`Permission.Changed`, `Permission.RowMappingChanged`). Platform Administrators have no permission endpoints and see object names only (never rows) when proposing the operation.

## Platform Insights (P7.1)
Organizations never touch the configuration tables: metrics run against `insights.*` views that expose `OrganizationId`, counts, codes, statuses and timestamps only (no names, e-mail addresses, subjects, descriptions, metadata JSON, hashes or secrets). The SQL is generated exclusively by `InsightsSqlBuilder` from the approved catalog with parameterized values, and `[OrganizationId] = @tenant` is bound from the authenticated principal; requests cannot reference the organization column at all. Queries use the dedicated login from `Insights:ConnectionString` (SELECT on the `insights` schema, DENY on `dbo`); the configuration page shows whether it is configured and confined, and development falls back to the configuration-database login with a logged warning. Platform Administrators maintain the global catalog and may preview SQL but cannot run organization queries. Organization Administrators have every approved metric and the organization dashboard; other organization users run only the metrics granted to their active roles (P7.2), and nothing lets a role of one organization be granted from another. Catalog changes are audited (`Insights.*`) and every metric query is a usage event.

## AI providers and query planning (P8.1)
Provider keys are encrypted with Data Protection (purpose `WabiInsight.Ai.ProviderCredential.v1`) and never returned; the owner keeps the platform Anthropic key in `appsettings.json` by decision, and the seeder encrypts it into the database at startup. Organization metadata goes only to an approved provider: the organization's selection if it is approved and its type is allow-listed, else the platform default; there is no fallback to an unapproved endpoint. The model receives the system prompt plus an authorized snapshot (approved, permitted objects and columns only; descriptions sanitized and delimited as data) and the sanitized question; it returns a typed plan that is parsed, shape-validated and authorized (objects, columns, application, row predicates from the user's own context) before anything else happens. Rejections return 422 with stable codes and are recorded as failed usage events; token counts and estimated cost are recorded on success. Row predicates are attached per object as parameters, never as text in the plan.

Since P13.8 a plan may filter on aggregated values, compare two columns and refer to the asker's own employee, department or section code. These add no new trust: compared columns are authorized like every other reference and must hold the same kind of value; aggregate conditions bind typed parameters; and the asker's codes are never sent to the model. The planner writes a placeholder (`$asker.department`), the authorizer reads the code from the authenticated user's own profile (the same source as row scopes), refuses the plan when the profile has none, and the compiler binds it as a parameter. A placeholder narrows a result; it never replaces or widens the row scopes, which are still applied inside each object's derived table.

## AI execution (P8.2)
The only SQL that reaches a business source is produced by the dialect compilers from an authorized plan: catalog identifiers quoted, every literal a typed parameter, row predicates applied inside a derived table per object before joins, a hard row cap and statement timeout, and a guard that rejects anything other than one SELECT. Execution uses the organization's own read-only connection (SQL Server READ COMMITTED, Oracle READ ONLY transaction) or the insights login for Platform Insights, where `OrganizationId = @tenant` is bound on every view. Interpretation receives a capped sample of rows per panel (at most 50 per panel, 240 in total) as delimited data and its output is sanitized before display. Failures surface as stable codes; raw database messages stay in the server log. A multi-panel answer (P8.3) is validated and authorized query by query before any of them runs; one rejected query rejects the whole answer, and every panel's SQL comes from the same compiler and guard.

## Reports, email drafts and logos (P8.3)
Report text and email drafts are model output over the verified rows, sanitized (control characters, delimiter look-alikes, length caps) before rendering or display; the PDF's charts, tables and KPI boxes are drawn from the panel data in code, so no model text can change a figure. The PDF is stored outside the web root through `IArtifactStorage` and served by `GET /api/ai/analyses/{id}/report` only to the user who ran the analysis (tenant filter plus explicit `UserId` check); a report is never attached to an email by the platform — the user downloads it. Organization logos are accepted from Organization Administrators only, limited to PNG/JPEG/SVG and 1 MB, checked against magic bytes, and SVGs are refused when they contain scripts, event handlers or foreign objects; the logo endpoint is served with `nosniff` and a sandboxing Content-Security-Policy.

## History (P9.1)
History entries, versions, artifacts and collections are tenant-owned; every service method filters by `OwnerUserId` on top of the tenant filter, so another user of the same organization sees 404 for an entry that is not theirs (sharing arrives in P10.1 as an explicit grant). Reopening a version streams the stored answer from artifact storage and never touches the business source; a re-run goes through the whole secure workflow again under the caller's current permissions, so a revoked column makes the re-run fail and the failure is recorded as a version instead of exposing the old rows as if fresh. Soft deletes keep the rows for audit and emit `History.Deleted`.

Exports (P9.2) are produced from the stored answer only — never from a fresh query — so an export can never show more than its version did. Every generated file is an owner-scoped artifact (same tenant filter plus `OwnerUserId` check on download), its generation is recorded in append-only `ReportGenerationEvents`, and the exporters write only values from the panel rows: model text is sanitized before it reaches a document, and no user text is interpreted as markup, formulas (cells are typed values, never formulas) or file names (file names are ASCII slugs).

## Sharing (P10.1)
Shares are explicit grants inside one organization: the recipient must be an active user found through the tenant filter, the share row references owner and recipient through composite keys into `OrganizationUsers` of the same organization, and the recipient's read path is a separate projection (addressed to me, not revoked, not expired, analysis not deleted) that exposes the stored answer and files of completed versions only — never a re-run, export, rename or delete, and never the owner's history endpoints. Expiry is checked at read time, revocation is immediate, and both are audited (`Share.Created`, `Share.Revoked`) and notified. Email delivery follows review B11: Restricted data never leaves the organization (any external address blocks the send), Confidential data needs the owner's explicit per-send disclosure approval, Internal data needs the standard confirmation; every attempt — sent or blocked — is an append-only `EmailDraftEvent` with the recipients, counts, classification and approval, plus `Share.EmailSent` / `Share.EmailBlocked` audit entries. Recipient addresses are validated, capped at ten, and the owner's subject and body are sanitized; attachments are kept in memory with the queued message and are never written to the outbox table. Google Drive and OneDrive publishing (P10.2) is deferred to the next version by owner decision, so no OAuth token is stored anywhere.

## Hardening (P12.1)
- **Response headers** (`SecurityHeadersMiddleware`, first in the pipeline so error responses carry them too): `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Permissions-Policy` (camera, microphone, geolocation, payment, USB denied), `Cross-Origin-Opener-Policy` and `Cross-Origin-Resource-Policy: same-origin`, `X-Permitted-Cross-Domain-Policies: none`, `Cache-Control: no-store` (unless the endpoint set its own), a `Content-Security-Policy` of `default-src 'none'; frame-ancestors 'none'; base-uri 'none'; form-action 'none'` on JSON responses and `frame-ancestors 'none'` on downloads; `Server` is never sent (Kestrel `AddServerHeader = false`). The Angular shell gets its own policy from nginx / IIS (`deploy/`), including `script-src 'self'`.
- **Request bodies**: `Security:MaxRequestBodyBytes` (1 MB) is enforced twice — `RequestBodyLimitMiddleware` answers 413 from the declared `Content-Length` before a byte is read and caps the server feature for chunked bodies, and Kestrel carries the same limit. Only the logo (`[RequestSizeLimit(2 MB)]`) and ticket attachment (10 MB) actions declare their own; a test asserts that these are the only ones.
- **Rate limits**: per client address on login and bootstrap (P1.3), per signed-in principal on `/api/ai/ask` and `/api/ai/plan` (`Security:AiRateLimitPerMinute`, 30) because each call spends model tokens and source queries, and a global budget per principal across the API (`Security:ApiRateLimitPerMinute`, 600). All answer 429 with `Retry-After`.
- **Cookies**: the session and antiforgery cookies are `HttpOnly`, `SameSite=Lax` and `Secure` in every environment but Development and Testing (which run over plain HTTP in-process).
- **Attachment scanning**: `ClamAvAttachmentScanner` streams every upload to clamd (INSTREAM) and fails closed — connection failure, timeout or an unexpected reply rejects the file (`scanner_unavailable` / `scanner_error`), `FailOpen=true` is an explicit opt-out; `AttachmentScanning:Provider=None` keeps the accept-all scanner for development. Rejections are `attachment_rejected_by_scan` to the client, with the signature in the server log only.
- **Errors**: unhandled exceptions become RFC 9457 problem details without exception text or stack traces (verified by a test), are counted as `Api.Error` usage events, and never echo request bodies.
- **Dependencies**: `dotnet list package --vulnerable --include-transitive` and `npm audit --omit=dev --audit-level=high` run in CI on every pull request; the only advisory at the time of writing (minimatch, development tooling) was fixed through an `overrides` pin.
- **Verification suite** (`tests/WabiInsight.IntegrationTests/Security/`): a cross-tenant sweep sends every tenant-owned route (33 probes across applications, metadata, structure, users, permissions, tickets, collections, history, shares, insights, platform organizations) with organization A identifiers as a user of organization B (404/403 only, and no organization-A marker in any body), anonymously (401 everywhere), as a platform administrator against business endpoints (403/404) and as an organization user without the administrator role against administration (403); it then scans `AuditLogs`, `UsageEvents`, `Notifications` and `EmailMessages` for the connection-string password and confirms the stored connection string is encrypted. A reflection test proves every controller action carries `[Authorize]` with a named policy except the five known public actions (CSRF token, login, bootstrap status/initialize, platform info) and the session-only auth actions covered by the fallback policy. Further tests cover the headers, the body limits (JSON refused at 1.2 MB, a 1.5 MB logo reaching validation), the AI and global rate limits, and error responses.

## Access ledger and scheduler (P14.1)

- **Ledger.** Every analysis writes one `AnalysisAccessFacts` row per object it touched, in the same unit of work as the analysis: user, role codes and department at that moment, application, catalogue object id (or the plain name when the object is unknown), columns and filter columns as catalogue ids, row count, highest classification, number of literal filter values and how many of those were on identifier columns (primary keys or identifier semantic roles), export format, and the outcome (`Succeeded`, `Rejected`, `Unauthorized`, `Failed`). Rejected and unauthorized plans are recorded too, because repeated attempts are a signal. Exports from My History are facts of their own. No business data values are stored: only counts, ids and names of objects and columns.
- **Append-only.** The DbContext refuses updates and deletes of facts. The only removal is the retention job's set-based delete of rows older than the organization's `MonitoringRetentionMonths` (owner decision D3: 24 by default, capped by `Monitoring:MaxRetentionMonths`).
- **Tenancy.** Facts and baselines are tenant-owned (EF filters plus write guards). Background jobs run under the platform scheduler principal and query with an explicit organization predicate through `AsPlatformScope`; nothing they compute leaves the organization it belongs to. Platform Administrators cannot read facts or baselines through any endpoint.
- **Scheduler.** `ScheduledJobs` rows are taken with an atomic conditional `UPDATE` (lease owner and expiry), so two API instances never run one job twice; a crashed instance's lease expires after `Monitoring:LeaseMinutes`. The next run is always strictly after now, so a long outage produces one run, not a burst. Failures are recorded on the job (`LastError`, `ConsecutiveFailures`) and as a `Scheduler.JobFailed` usage event; the `scheduler` operations health check reports overdue and repeatedly failing jobs.
- **Semantic roles.** `DatabaseColumns.SemanticRole` is a hint for rule templates (Phase 14) set only by the Organization Administrator through the existing column update (audited with the column). The API suggests a role from the column name and type; a suggestion is never stored by itself and roles never grant or restrict access.

## Monitoring Rules and Alerts (P14.2)

- **Run as the owner, never wider.** Every rule has an owner. Data rules are compiled into ordinary query plans and evaluated in a DI scope signed in as that owner, through the same validator, authorizer (column grants, row scopes) and read-only executor as the owner's questions. Save-time validation runs the same checks. An owner without permission on the object or a column is refused at save time; if access is lost later, the rule is paused and flagged, not run. Organization Administrators have no data access by role, so a rule they own cannot read business data; they choose an owner who can.
- **Who sees what.** Rules: administrators (all), Management (their own data rules); everyone else is refused. Alerts: administrators, the rule's owner and author, and its recipients. Group values and measures of data alerts are shown (in the app, the test run and the digest) only when the viewer's own permissions cover the rule's object and the grouped and measured columns; otherwise titles and counts only. In-app notifications carry the rule name and count, never group values. Platform Administrators get per-organization counts only and are refused on every organization endpoint.
- **Human decisions (D2).** Alerts never change users or data. Acknowledge, resolve and dismiss are recorded as `AlertEvents` with the actor and a note (required to resolve or dismiss) and audited (`Alert.StatusChanged`). Suspension is offered only to administrators, only for access alerts about a user, after a confirmation, and goes through the existing user service (security stamp rotated, own account and last administrator protected), audited as `Alert.UserSuspended`.
- **Append-only and retention.** `RuleEvaluations` and `AlertEvents` refuse updates and deletes through the DbContext; the runtime login denies `UPDATE` on them and on `AnalysisAccessFacts`. The nightly retention job removes evaluations and closed alerts older than the organization's retention, set-based.
- **Tenancy.** Rules, recipients, evaluations, alerts and events are tenant-owned (EF filters, write guards, composite foreign keys to the organization's users and roles). Scheduled runs use the platform scheduler principal with explicit organization predicates; evaluation itself always runs as an organization user of that organization.

## Natural-language and system rules (P14.4)

- **No model output runs unconfirmed.** The draft endpoint returns a proposal and writes nothing. The model returns object and column names only; the server binds them to the rule owner's permitted, approved catalogue entries (an unknown or unpermitted name rejects the draft), then runs the save-time validation and the owner's authorization. The user saves through the normal rule endpoint, where the same checks run again.
- **What the model sees.** Only the owner's permitted catalogue (names, types, field roles, display names), today's date and the description, fenced as data and sanitized (control characters, fence markers) like the §19 planner. No ids, no rows, no other organization's metadata. Drafts are rate-limited with the AI policy and recorded as usage events with tokens and estimated cost.
- **System rules.** Administrators only (Management and analysts are refused); they count the organization's own platform events (failed executions, failed connection tests, failed outbox emails, removed catalogue entries, failed report deliveries, month-to-date AI cost) under tenant filters plus explicit organization predicates for the outbox. No business data is read or shown.
- **Rule health.** A catalogue change that removes or unapproves an object or column pauses every dependent data rule immediately, with an alert to its owner and author; a paused rule cannot resume until its definition validates again.

## Periodic Reports (P14.3)

- **Each recipient's own figures.** A run never reuses the stored result. For every recipient, the analysis's stored plan is re-validated and re-authorized against that recipient's permissions and row scopes in a scope signed in as the recipient, then executed read-only. Recipients without permission receive a "no data for your permissions" email without a file. The owner's AI narrative and written study describe the owner's figures, so they are left out of every delivered file.
- **Consent and authority (D6).** Only Organization Administrators (any active users of the organization, up to 50) and Management users (themselves only) create subscriptions. The analysis must be the author's own or explicitly shared with the author by its owner; resuming re-checks this.
- **Files.** Delivered files live in artifact storage and are downloadable only by their recipient (`/api/subscriptions/received/{id}/file`); not the author, not an administrator. Emails carry the attachment and a link to the app; the outbox keeps attachments in memory only.
- **Log and failures.** `ReportDeliveries` is append-only (DbContext guard); retention removes old files and rows. Three failed scheduled runs pause the subscription and notify its creator. Changes are audited (`Reports.Subscription*`); runs are usage events (`Reports.SubscriptionDelivered` / `Failed`).
- **Tenancy.** Subscriptions, recipients and deliveries are tenant-owned with composite foreign keys to the organization's users; Platform Administrators are refused on every subscription endpoint.

## Audit
`AuditLogs` is append-only (application guard plus `scripts/sql/create-runtime-login.sql`). Records carry actor type/id, event code, entity, JSON details without secrets, correlation id and client IP.
