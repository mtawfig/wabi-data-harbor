# Wabi Insight — Architecture

Status: P1.1 skeleton, P1.2 configuration database and tenant core, P1.3 authentication and bootstrap; each phase extends the relevant section.

## Three logical layers

| Layer | Location | Responsibility |
|---|---|---|
| 1 — Angular web application | `src/web` | One Angular 22 app with public, organization and platform areas (EN/AR, LTR/RTL). |
| 2 — ASP.NET Core Web API | `src/WabiInsight.Api` (host) + `src/WabiInsight.Core` (domain, services, interfaces, query-plan model, compilers) + `src/WabiInsight.Infrastructure` (EF Core, DB adapters, providers) | One deployable API. The two class libraries are build organization inside this layer, not extra layers. |
| 3 — Data and integrations | SQL Server configuration DB, organization SQL Server/Oracle sources, LLM endpoints, SMTP, Google Drive, OneDrive, artifact storage | Reached only through Infrastructure. |

## Configuration database (P1.2)

One SQL Server database, EF Core 10, migrations in `src/WabiInsight.Infrastructure/Persistence/Migrations`, applied by `dotnet run --project src/WabiInsight.Api -- migrate` at deployment time (never by a web request).

Conventions: UUID v7 keys generated in code (`Ids.New()`), `datetimeoffset` UTC timestamps stamped by the context, `rowversion` concurrency tokens on editable aggregates, enum codes stored as strings with check constraints.

### Onboarding (P2.1)

`OrganizationService.CreateAsync` runs in one transaction: organization row → system roles from `SystemRoles.Templates` → built-in Platform Insights application → initial Organization Administrator through `OrganizationUserProvisioningService` (user, login identity, `OrganizationAdmin` role, audit) → temporary password emailed through the outbox. Role codes are loaded into the principal at login and on security-stamp revalidation, so the `OrganizationAdmin` policy and the admin navigation follow the stored assignments.

### Organization administration (P2.2)

`OrganizationUserService`, `OrganizationStructureService`, `RoleService` and `RoleTemplateService` throw `DomainException` with a stable outcome and error codes; `DomainExceptionHandler` maps them to problem responses (404/409/400) and `TenantContextException` to 403, so controllers stay thin and the Angular `problemMessage` helper localizes the codes. Guards: an administrator cannot deactivate themselves or drop their own admin role, and the organization always keeps at least one active administrator. Role changes rotate the user's security stamp so open sessions pick up the new roles.

### Usage metrics (P3.1)

`IUsageEventWriter` appends `UsageEvents` inside the same unit of work as the business change (login, failed login, logout, password change, organization created/status changed, user and administrator created, email queued/sent/failed, unhandled API errors). `PlatformMetricsService` aggregates per day in SQL (`GROUP BY CAST(CreatedAt AS date)`) and buckets by day/week/month in memory; it reads identity tables and the event stream only, so application names, prompts and business data never reach the platform dashboard. Organization-scoped metrics for the organization dashboard (P7.2) reuse the same stream through the tenant filter.

### Support desk (P4.1)

`SupportTicketService` resolves the caller's role from the tenant context only (requester, OrganizationAdmin of the ticket's organization, or Platform Administrator) and applies the §15.3 transition table through the pure `TicketStateMachine`. Platform reads use `AsPlatformScope`; organization reads go through the tenant filter plus a `CreatedByUserId` restriction for non-administrators. The first platform view records `FirstOpenedBy/At`, a `TicketViewed` timeline event and `NEW → READ` exactly once; later views only write an audit row. A requester or OrganizationAdmin reply on `PendingUserResponse` moves the ticket back to `Started` automatically. Attachments are limited to 10 MB and an extension allow-list, hashed, passed through `IAttachmentScanner` (no-op by default) and stored by `FileSystemArtifactStorage` under `Storage:RootPath` with random object names; platform downloads are audited (review C6). `NotificationDispatcher` writes `Notifications` rows in the same unit of work and queues bilingual emails through the outbox after the change is saved. Ticket KPIs (open tickets, critical incidents, tickets created, average first response and resolution) are now collected by `PlatformMetricsService`.

### Support access (P5.1)

`SupportOperations.Catalog` is the typed operation list (specification §16.2): `CreateOrganizationUser`, `ResetOrganizationUserPassword`, `ConfigureRole`, `UpdateOrganizationSettings` are executable now; `UpdateTablePermissions`, `RefreshMetadata`, `DiagnoseApplicationConnection` can be proposed but execute only once Phase 6 ships their services. `SupportAccessService` runs the lifecycle: a Platform Administrator proposes operations with specific targets on an open ticket (targets validated against the ticket's organization, one open grant per ticket; before a grant the targets offered are the requester and the standard roles, with exact look-ups by e-mail address or role code, and a proposal to create a user names the address) → an active `OrganizationAdmin` of that organization approves (the requester may self-approve unless `RequireSecondAdminApprovalForSupportAccess`) or declines → the assigned administrator enters support mode (one session at a time) → operations run → complete, revoke (any OrganizationAdmin or any Platform Administrator, ends the session immediately) or expire (default 4 h, max 72 h; lazily on access plus a one-minute `SupportAccessExpiryWorker` sweep). `SupportAccessAuthorizer` is the dedicated handler: it resolves the caller's active session and checks assignment, expiry, operation and target against the pure `SupportAccessScope`; every denial is audited. `CreateOrganizationUser` has target type `AssignableRole`: its (optional) targets are the role ids the new user may be given, shown to the approver with the grant, and `AuthorizeRoleAssignmentAsync` refuses any requested role that the grant does not list (`support_role_not_granted`), so the roles are part of what the organization approved and never come from the execute payload alone. `SupportOperationExecutor` performs the operation with explicit `OrganizationId = grant.OrganizationId` queries (never through an impersonated organization principal) and records administrator, organization, ticket, grant, session, operation, target and outcome on the ticket timeline, in `AuditLogs` and in `UsageEvents`, and notifies the organization's administrators. The `SupportMode` authorization policy guards the execute endpoint.

### Applications and metadata (P6.1)

`ConnectionStringProtector` wraps ASP.NET Core Data Protection with the purpose `WabiInsight.Applications.ConnectionString.v1`; keys are persisted under `DataProtection:KeyRingPath` (outside the database and web root) with a 90-day lifetime and old keys kept for decryption. The fingerprint is an HMAC-SHA256 over the adapter-normalized string keyed with a random salt stored once in `PlatformSettings`, so an already-registered source is rejected for any organization (A7) without revealing anything. `IDatabaseAdapter` (`SqlServerAdapter`, `OracleAdapter`) normalizes strings (read-only intent, short timeouts), builds the display hint, tests connectivity with a read-only verification of the account, and discovers the catalog from `sys.*` / `ALL_*` views only. `ApplicationService` (OrganizationAdmin, tenant filter) creates and edits applications, replaces and tests connections, and toggles approval; plain text exists only inside the request. `MetadataService` merges a discovery into the catalog with a diff: new objects and columns stay unapproved, missing ones are flagged `IsPresent = false` and keep their approvals and names; `RefreshForOrganizationAsync` is the explicitly scoped entry used by the support executor for the `RefreshMetadata` grant operation, and `DiagnoseApplicationConnection` runs the adapter test under a grant. Platform Administrators have no application endpoints at all.

### Permissions (P6.2)

`RoleTableGrant` / `RoleColumnGrant` / `RoleRowGrant` (tables `RoleTablePermissions`, `RoleColumnPermissions`, `RoleRowPermissions`) and `RowScopeColumnMapping` (`RowScopeColumnMappings`, one per object) carry composite foreign keys that include `OrganizationId`, so a grant can never point at a role or object of another organization. `PermissionService` (Organization Administrators; the support executor calls the explicitly scoped overload under a grant) validates that the object is approved and present, that listed columns are approved columns of that object, that a row scope is chosen, and refuses edits to `Management` (`management_role_automatic`). `PermissionCombiner` is pure: union of columns across roles (an *all approved columns* grant expands at resolution time, so columns approved later are included), OR of row scopes, `All` dominates, and a scope without a mapped column on the object is reported as unmapped and yields no rows. `PermissionResolver.ResolveForUserAsync` evaluates in this order: organization boundary (never widened; platform principals only through `AsPlatformScope`), approved and active non-built-in applications, approved and present objects and columns, then the user's active roles via `UserRoles`; `Management` contributes every approved object with `All`; the row-scope context is the user's employee number, department code and section code. The query engine (P8) consumes `EffectivePermissions` and must never bypass it.

### Platform Insights data source (P7.1)

The built-in `WI-INSIGHTS` application has no connection string: every organization reads the same `insights` schema of SQL views over the configuration database (`InsightsSchema.Views`, created by the `AddPlatformInsights` migration with `CREATE OR ALTER VIEW`). Every view carries `OrganizationId`; views expose counts, codes, statuses and timestamps only. The catalog (`InsightsObjects`, `InsightsColumns`, `InsightsMetrics`) is global and has no `OrganizationId`: it is the one place where that is allowed, and it is maintained by Platform Administrators through `InsightsCatalogService` (sync against `INFORMATION_SCHEMA`, labels, approval, metric definitions). `InsightsSqlBuilder` is the only producer of insights SQL: identifiers come from the approved catalog and are bracket-quoted, values are parameters, the first predicate is always `[OrganizationId] = @tenant`, and the organization column can neither be filtered nor grouped. `InsightsQueryService` binds `@tenant` from `ITenantContext` and opens the connection through `IInsightsConnectionFactory`, which uses the dedicated read-only login from `Insights:ConnectionString` (created by `scripts/sql/create-insights-login.sql`, SELECT on the `insights` schema only) and falls back to the configuration-database login in development with a visible warning on the configuration page. Platform Administrators can preview the SQL of a metric but never execute it; P8's compiler will target the same views with the same predicate.

### Organization dashboard and metric grants (P7.2)

`InsightsQueryService.GetDashboardAsync` composes the Organization Administrator dashboard entirely from approved catalog metrics run through the builder (so every number carries the organization predicate) and zero-fills the series over the requested period; applications and department names are joined from the tenant-filtered configuration tables. `RoleMetricGrant` (`RoleMetricPermissions`, composite FK with `OrganizationId` to the role) assigns approved metrics to roles; `MetricGrantService` manages them and `AllowedMetricsAsync` resolves what a user may run: every approved metric for `OrganizationAdmin`, otherwise the union over the user's active roles. The Organization Insights page and, from P8, natural-language questions over Platform Insights use that same allowed set.

### Secure AI engine: providers and query plan (P8.1)

`IAiProvider` adapters (`AnthropicProvider`, `OpenAiCompatibleProvider`, `GeminiProvider`) share one named `HttpClient` and one contract: system prompt, user content, optional JSON schema, max output tokens and effort in; text, usage and stop reason out. Each adapter asks its vendor for schema-constrained JSON and maps failures to stable codes (`ai_provider_unauthorized`, `ai_provider_refused`, ...). **Prompt caching (P13.21):** the planner's user turn is built in two parts (`PromptBuilder.BuildPrompt`): the catalogue (METADATA block, the same for every question on one application with the same permissions, relationships sorted so it is byte-identical) goes in `AiRequest.SharedContext`, and the language, question and date follow in `UserContent`. `AnthropicProvider` sends the system prompt and the catalogue as two cache breakpoints (`cache_control: ephemeral`, five minutes) and the question as an uncached block; the other adapters receive the two parts joined. Usage carries cache reads and writes, and `EstimateCost` prices cache writes at 1.25 times the input price and cache reads at the provider's cached price. A cache entry is reused only for byte-identical content inside the platform's own Anthropic account, so caching never changes what a user may see. `AiProviderService` owns `AIProviderConfigurations`: platform rows (approved, one default) and organization rows (own key, type inside the `Ai.AllowedProviderTypes` allow-list); keys are Data Protection encrypted with their own purpose and only a hint is ever returned. `ResolveForOrganizationAsync` returns the organization's selection when it is still approved and allow-listed, otherwise the platform default, never anything else. `AiProviderSeeder` keeps the platform default in sync with `Ai:Anthropic` in configuration. `QueryPlan` is the only artifact the model produces; `QueryPlanValidator` and `QueryPlanAuthorizer` are pure and unit-tested; `QueryPlanner` builds the authorized metadata snapshot from `IPermissionResolver`, calls the provider, and returns an `AuthorizedPlan` whose objects carry the row predicates the P8.2 compiler must apply at the source-table level. No SQL exists yet at this stage.

### Secure AI engine: compilation, execution, interpretation (P8.2)

`ISqlDialectCompiler` (`SqlServerCompiler`, `OracleCompiler`; `PlatformInsights` maps to SQL Server) turns an `AuthorizedPlan` into one parameterized SELECT. Each object becomes a derived table that carries its own row predicates (`(SELECT * FROM [dbo].[Orders] WHERE [DeptCode] = @p0 OR ...) [o]`), so scoping happens before joins and aggregations; literals become typed parameters (converted against the catalog column type, including the row-predicate values), `SUM`/`AVG`/`MIN`/`MAX` over yes/no (`bit`) columns are cast to numbers, identifiers are bracket or double-quote quoted, and a final guard refuses anything that is not a single SELECT without separators or comments. `QueryExecutor` opens the organization's own connection (decrypted for the call, read-only intent, READ COMMITTED on SQL Server, `SET TRANSACTION READ ONLY` on Oracle; the insights login for the built-in application), applies the statement timeout and row cap, and returns typed rows. `ResultCalculator` derives totals, averages, ranges and chart series deterministically in code. `AnalysisService` orchestrates planning, compiling, executing, calculating and the interpretation call (rows passed as delimited data; a failed narrative never fails the answer; since P13.7 each panel also states whether it is complete and which row scopes limited it, so the narrative never presents a permission-filtered or partial result as the whole picture, and the page shows the same access note) and records `AnalysisExecutionMetrics` and usage events; the P9 workspace will persist the analysis itself. Since P13.8 the plan carries `having` (conditions on aggregate select aliases, compiled to `HAVING` against the aggregate expressions; counts bind as integers, sums and averages as decimals, MIN/MAX as the column type), `PlanCondition.CompareTo` (column against column, type families must match, both columns authorized) and `AskerValues` placeholders (`$asker.employee|department|section`) that `QueryPlanAuthorizer` resolves from `RowScopeContext` into `AuthorizedPlan.AskerValues` and the compiler binds as parameters; the snapshot marks the organization's row-scope columns with `askerKey`. To stay inside the providers' structured-output grammar limit, optional strings in the schema are plain strings (`""` = none) that the model classes read as null, and `having` is a flat list. **Correct numbers and periods (P13.24):** the SQL Server dialect averages whole-number columns as `float` and totals them as `bigint` (T-SQL would cut an average to a whole number and overflow an `int` total); a filter value written as a date only stands for that whole day, so on columns that store a time of day (every date type except SQL Server `date`; Oracle `DATE` included) `eq`, `neq`, `gt`, `lte`, `between` and `in` compile to ranges ending before the next day; and `RelativeDates` (`$today`, `$week_start`, `$month_start`, `$quarter_start`, `$year_start`, optionally ± N `d`/`w`/`m`/`q`/`y`) let the planner store "this month" or "the last 30 days" as such: `QueryPlanAuthorizer` resolves them against today in the organization's time zone at every run (ask, re-run, periodic report), so a stored plan follows the calendar. The planner is told the organization's local date, and the web app describes these values in words ("the start of last month").

Since P8.3 the planner's artifact is an `AnalysisPlan`: an objective, assumptions and one to ten `QueryPlan`s (each with a title), produced under the `wabi_analysis_plan` schema that shares its `$defs` with the single-query schema. `QueryPlanValidator.ValidateAnalysis` validates the count and every query; `QueryPlanner` authorizes each query separately and rejects the whole answer if any reference is not permitted; `AnalysisService` compiles and executes the queries one by one (same connection rules, same caps), returns `AskResponse.Panels` (title, plan, redacted SQL, result) and runs one interpretation over all panels. `ResultCalculator` turns a second category column next to the x axis into one series per value. The planning call gets at least `AnalysisPlanSchema.MinPlanOutputTokens` (8,192) output tokens and a cut-off plan is reported as `plan_output_truncated`.

Reports and email drafts (specification §20): the plan's `deliverables` say whether the user asked for a study (`report`) or an email (`email`). After execution, `ReportComposer` sends the question, objective and every panel's verified rows (capped per panel and in total) to the provider under the `wabi_report` schema and sanitizes the result (title, introduction, sections with panel references, summary, key findings, recommendations, email); panels the model forgot are appended so nothing verified is dropped. `QuestPdfReportRenderer` (`IReportRenderer`, QuestPDF with embedded Inter / IBM Plex Sans Arabic) draws the PDF from the panel data — `SvgChartBuilder` for bar/line/pie (since P13.17 `ChartComposer` draws its shapes as SVG and its labels with the QuestPDF text engine, so Arabic labels are shaped and laid out right to left), QuestPDF tables for rows, KPI boxes for single numbers — with the organization logo in the header of every page and page numbers in the footer. The PDF goes to `IArtifactStorage` under `analysis-reports`; `AnalysisExecutionMetrics.ReportArtifactKey/ReportFileName/ReportSizeBytes` record it and `OpenReportAsync` serves it to the user who ran the analysis. The organization logo lives in `Organizations.LogoArtifactKey/LogoContentType` (category `organization-logos`).

### Persistent history (P9.1)

Step 17 of the workflow: `AnalysisService.AskAsync` ends by creating an `AnalysisHistory` entry (or, for a re-run, bumping the saved entry's version) and an `AnalysisHistoryVersion` with the plan, the redacted SQL, a result summary and the stored answer as an artifact; the PDF produced for a report becomes a second artifact of the same version. `AnalysisHistoryService` serves `/api/history`: lists and details are projections over the owner's entries, the stored answer is read back from the artifact (never recomputed), and `RerunAsync` calls `AskAsync` with the saved prompt and the history id so the outcome lands as the next version — including failed outcomes, which are recorded as failed versions. Deleting is a soft delete with an audit event; artifacts stay with the version.

### Reports and exports (P9.2)

`ExportAsync` reads the stored answer of a version, builds `ReportContent` (`AnswerReportBuilder`: the written study when the answer had one, otherwise summary, key findings, headline numbers and results from the verified panels) and hands it to the PDF renderer or to an `IAnswerExporter` (`DocxExporter` with the Open XML SDK, `XlsxExporter` with ClosedXML). Charts in DOCX and XLSX are the same charts the PDF draws (shapes and labels through `ChartComposer`), rasterized to PNG by `ChartImageRenderer` through QuestPDF's Skia backend, at the chart's real height. A long table is shortened in the documents (the first 60 rows in the PDF, the first 100 in Word) and is then followed by one line in the document's language giving the real numbers in business words (`QuestPdfReportRenderer.ShortenedTableNote`: "Showing the first 60 of 312. The Excel export has the full list.", or "… of more than 1,000. The Excel export has the first 1,000." when the result itself stopped at its size limit); the workbook always has every row of the result. Headline figures are all drawn, at most five side by side and the rest on further rows (`KpiRows`). The file is stored as an `AnalysisArtifact` of kind `ExportPdf/ExportDocx/ExportXlsx` under `analysis-exports`, a `ReportGenerationEvent` is appended (also for failures), and the reports library (`ListReportsAsync`) is a projection over the owner's artifacts other than the result JSON. Arabic output is right-to-left in all three formats (QuestPDF content direction, Word `BiDi`/`BiDiVisual`, Excel `RightToLeft`), and sample files produced by the unit tests live under `tests/fixtures/exports/`.

### Sharing (P10.1)

`SharingService` serves `/api/shares` and the `shares`/`email` routes under `/api/history/{id}`. Owners (the `Mine` projection: `OwnerUserId == UserId`, not deleted) share with colleagues looked up through the tenant filter and an explicit `Active` status check; sharing again with the same colleague refreshes the message and expiry instead of creating a second row. Recipients read through the `Received` projection only (addressed to them, not revoked, not expired, analysis not deleted): the detail, the stored answer and the study PDF of completed versions. Nothing else is reachable through a share — re-run, export, rename, archive, delete and collections stay owner-only, and the history endpoints keep answering 404 to a recipient. Every share and revocation writes a notification (`Analysis.Shared`, `Analysis.ShareRevoked`), a bilingual email through the outbox and an audit entry.

Email delivery (`SendEmailAsync`) classifies each address as internal (an active user of the organization) or external and applies the review B11 rules before anything is queued: Restricted data with any external address is blocked (`share_restricted_external_blocked`), Confidential data requires the owner's explicit per-send `disclosureApproved` flag (`share_disclosure_approval_required`), Internal data needs the client's standard confirmation. Blocked and sent attempts both append an `EmailDraftEvent`; the model's own drafts append a `Drafted` event when the answer is stored, so drafts and sends are distinguishable (specification §12.3). The attachment is the version's study PDF, or the answer rendered to PDF through `ExportAsync` (which also lands in My Reports). Internal recipients also receive an in-app share so the link in the email opens the stored analysis; the email body is the owner's text inside `EmailTemplates.SharedAnalysis`, and `EmailMessage.Attachments` travels with the message in memory only — the outbox row never stores bodies or files. `SmtpEmailSender` attaches the files through MimeKit.

### Tenant core

- `TenantPrincipal` is the trusted identity (type, organization, user/administrator id, roles, department, section). `TenantContext` is scoped per request, initialized once by the authentication middleware (P1.3) and read through `ITenantContext`.
- `ConfigurationDbContext` applies a global query filter `OrganizationId == CurrentOrganizationId` to every `ITenantOwned` entity. Anonymous and platform-administrator scopes see **no** tenant rows by default.
- `AsPlatformScope(tenantContext)` is the only sanctioned cross-organization read; it throws for anything but a platform administrator and callers must apply field-level restrictions.
- Write guard in `SaveChanges`: `OrganizationId` must be set, organization users cannot write outside their organization, anonymous scopes cannot write tenant data, `AuditLogs` cannot be modified or deleted.

### Test strategy

Integration tests run against a real SQL Server: `WI_TEST_SQLSERVER_CONNECTION` (CI service container or a local instance) or, when absent, a Testcontainers SQL Server 2022 container. A fresh database is migrated per run and seeded with two organizations, one user each, and one administrator. SQLite or in-memory providers are never used because constraints, filtered indexes and `rowversion` must be verified on the real engine.

## Request pipeline (P1.3)

`SecurityHeadersMiddleware` (P12.1) → `UseExceptionHandler` (RFC 9457 problem details) → `UseStatusCodePages` → HSTS (non-development) → HTTPS redirection → rate limiter (global per-principal budget, login/bootstrap per address, AI per user) → cookie authentication (with security-stamp revalidation) → `TenantContextMiddleware` (claims → `TenantPrincipal`) → `PasswordChangeRequiredMiddleware` → authorization (fallback: authenticated) → `RequestBodyLimitMiddleware` (P12.1) → MVC with the `AntiforgeryValidationFilter` → controllers. Health endpoints are mapped with `AllowAnonymous`.

Background work: `EmailOutboxWorker` (hosted service) consumes an in-process bounded channel fed by `EmailOutbox`, sends through the configured `IEmailSender` (`SmtpEmailSender`, `FileEmailSender`, `NullEmailSender`) and records the outcome on the `EmailMessages` row through `IEmailDeliveryLog`. A failure while sending or recording one message is logged and the worker goes on to the next one; no exception leaves the hosted service (that would stop the API). On shutdown the worker keeps sending what it already holds for `Email:ShutdownGraceSeconds` (default 20; retries then run without the retry delay), and the host's shutdown timeout is raised to at least that plus 10 seconds. Message bodies are never stored, so a row left `Queued` by a process that is gone can never be sent: after start-up the worker marks such rows `Failed` with `LastError = process_restarted_before_delivery` and writes the `Email.Failed` usage event (first the rows older than a two-minute safety margin, and two minutes later the rows queued before this process started; a conditional update per row makes it safe when several instances start together). The `email-outbox` health check reports them in `failedLast24h` and separately in `notSentBeforeRestartLast24h`.

CLI commands handled before the pipeline starts: `migrate` (apply migrations), `bootstrap` (create the first Platform Administrator), `seed-demo` (Development only), `storage-check` and `storage-copy` (file storage). See `docs/SECURITY.md` for the authentication design.

### Proactive agent (Phase 14)

**P14.1 (delivered):** `IAccessFactRecorder` writes `AnalysisAccessFacts` from `AnalysisService` (success, rejection, authorization failure, execution failure) and from `AnalysisHistoryService.ExportAsync`; `AccessFactExtractor` (Core, pure) turns query plans into per-object column, filter and row summaries. `ScheduledJobRunner` provisions per-organization standing jobs (baselines 02:15, retention 03:30, organization time zone), leases due jobs with a conditional `ExecuteUpdate`, and dispatches to `IScheduledJobHandler`s (`AccessBaselineJob`, `RetentionPurgeJob`); `JobSchedulerWorker` ticks it every minute when `Monitoring:SchedulerEnabled`. `JobRecurrence` computes next runs in local time. `ColumnRoleSuggester` proposes `DatabaseColumns.SemanticRole` values returned on `ColumnDto`. Migration `AddAccessLedgerAndScheduler`.

**P14.2 (Monitoring Rules and Alerts):** Core holds the typed `RuleDefinition` with `RuleDefinitionValidator`, the pure `DataRulePlanBuilder` (rule → `QueryPlan`) and the `RuleTemplates` catalogue (slots expressed as field roles). Infrastructure: `RuleCatalog` checks a definition against the catalogue and an `EffectivePermissions`; `RuleEvaluator` evaluates in a child DI scope initialized with the owner's `TenantPrincipal` (data rules through validator → authorizer → dialect compiler → `IQueryExecutor`; access rules over `AnalysisAccessFacts` and `AccessBaselines`); `RuleRunner` persists the outcome in the caller's scope (scheduler or same-organization user), applies the cooldown, raises `Alerts`/`AlertEvents`, notifies High alerts and pauses invalid rules; `MonitoringRuleJob` and `AlertDigestJob` are new `IScheduledJobHandler`s, and `EnsureStandingJobsAsync` now also keeps one digest job per organization and one job per active rule. `MonitoringRuleService`, `AlertService` (suspension through `IOrganizationUserService`) and `PlatformMonitoringService` back `MonitoringRulesController`, `AlertsController` and `PlatformMonitoringController`. Angular: `features/monitoring` (rules, alerts), `core/monitoring`, field-role picker in Metadata. Migration `AddMonitoringRulesAndAlerts`.

**P14.4 (natural-language and system rules):** `RuleDraftSchema` (Core) holds the `wabi_monitoring_rule` prompt, the strict JSON schema and the fenced user content built from the owner's permitted catalogue; `MonitoringRuleService.DraftAsync` calls the organization's `IAiProvider` through `IAiProviderResolver`, binds the returned names to catalogue ids and runs the save-time validation, returning a `RuleDraftDto` without writing a rule. `RuleEvaluator` gains the `System` kind (counts over `AnalysisExecutionMetrics`, `Applications`, `EmailMessages`, `DatabaseObjects`/`DatabaseColumns` and `ReportDeliveries` inside the organization; `AiSpend` sums the month-to-date estimated cost). `RuleHealthChecker` owns pausing (disable job, `rule_invalid` alert, notification) and is called by `RuleRunner` and by `MetadataService` after every catalogue change. `Organizations.MonthlyAiBudget` (migration `AddSystemRulesAndAiBudget`).

**P14.3 (Periodic Reports):** `ReportSubscriptions`, `ReportSubscriptionRecipients` and the append-only `ReportDeliveries`. `PeriodicReportRunner` (caller scope: scheduler or same-organization author) loads the analysis's latest completed plan and, for each active recipient, opens a child scope signed in as that recipient where `PeriodicReportRenderer` calls `IQueryPlanner.AuthorizeStoredAsync` (shape + authorization of a stored plan, no model call), compiles and executes the queries read-only and renders PDF (`IReportRenderer`) or XLSX (`IAnswerExporter`) from the panels only. The runner stores the file (`IArtifactStorage`, category `report-deliveries`), queues the email with attachment through `IEmailOutbox`, writes the delivery row and counts consecutive failures. `ReportSubscriptionJob` is the scheduled handler; `EnsureStandingJobsAsync` keeps one job per active subscription; `PeriodicReportService` and `PeriodicReportsController` (`/api/subscriptions`) expose management and "sent to me". Angular: `features/monitoring/periodic-reports`, "Sent to me" tab in My Reports. Migration `AddPeriodicReports`.


Design: [`PROACTIVE_AGENT.md`](./PROACTIVE_AGENT.md). Inside the same API: an append-only `AnalysisAccessFacts` ledger written with every analysis, a `ScheduledJobs` table with atomic leases driven by one `BackgroundService` (like the email outbox worker), a typed monitoring-rule document validated and authorized like the query plan and compiled by the same dialect compilers for data rules, an access-rule evaluator over facts and 28-day baselines, `Alerts` with a daily digest through the `EmailMessages` outbox and immediate `Notifications` for High severity, and `ReportSubscriptions` that re-run saved analyses per recipient under that recipient's permissions and deliver PDF/XLSX through the outbox.
